NekoDroid welcomes contributions. Before opening a pull request, follow the checks, staging rules, and conventions documented here. All changes to the emulator core or HLE path should be grounded in tests and the existing source style.

<Note>
  All work happens at the repo root (`src/`, `public/`). Do not publish a nested `browser-droid/` folder or local working copies.
</Note>

## Setup

You need Rust stable with the `wasm32-unknown-unknown` target, `wasm-pack`, and Node.js installed.

<Tabs>
  <Tab title="Clone and install">
    ```bash
    git clone https://github.com/nishal21/NekoDroid.git
    cd NekoDroid
    npm install
    ```
  </Tab>
  <Tab title="Build Wasm">
    ```bash
    wasm-pack build --target web
    ```
  </Tab>
  <Tab title="Start dev server">
    ```bash
    npm run dev
    ```

    Open `http://localhost:5173` in your browser.
  </Tab>
</Tabs>

## Checks before a PR

Every change must pass these three commands before it can be merged.

<Steps>
  <Step title="Run Rust unit tests">
    ```bash
    cargo test --lib
    ```

    The suite includes 116+ tests covering memory read/write, UART MMIO, CPU fetch-decode-execute, ALU operations, branch logic, barrel shifter, load/store, block transfer, SWI exceptions, Thumb instructions, and HLE Dalvik stubs.
  </Step>
  <Step title="Build Wasm">
    ```bash
    npm run build:wasm
    ```

    This runs `wasm-pack build --target web` and must complete without errors.
  </Step>
  <Step title="Full production build">
    ```bash
    npm run build
    ```

    This builds Wasm, compiles TypeScript, and runs Vite production bundling. It must complete cleanly.
  </Step>
</Steps>

## Safe staging rules

Do not run `git add .` or `git add -A`. Those commands pull in local junk that should never be committed.

<Warning>
  Never stage these directories or files:

  - `browser-droid/` (local nested working copy)
  - `pkg/`, `target/`, `node_modules/`, `dist/`
  - `test-images/`, `*.zImage`, `*.img`, `*.cpio.gz`
  - `learning-journal.md`, `handoff-devlog.md`, `.cursor/`, `.env*`
  - Accidental CRLF-only edits to files you did not intend to change
</Warning>

### Recommended safe staging command

For APK HLE and core emulator work, stage only the allowlisted paths:

```powershell
git add -- `
  .gitignore .gitattributes `
  Cargo.toml Cargo.lock `
  package.json package-lock.json `
  README.md LICENSE CONTRIBUTING.md DEVLOG.md rust-toolchain.toml `
  .github/workflows/ci.yml `
  docs/ examples/hello-apk/ public/_headers `
  src/android/ `
  src/lib.rs src/main.ts src/cp15.rs src/cpu.rs src/cpu/tests.rs `
  src/memory.rs src/memory/tests.rs `
  testdata/
git add -u -- src/counter.ts src/typescript.svg
```

After staging, run `git status` and confirm that `browser-droid/`, `pkg/`, journals, and demo binaries are not listed.

### Leave demo binaries alone

Do not modify existing demo binaries unless you are deliberately changing them:

- `snake.*`
- `theremin.*`
- `vram_test.*`
- `input_test.*`
- `program.*`

## DEVLOG conventions

Track significant work sessions in `DEVLOG.md` at the repo root. Each session should record:

- Date and role
- What was built or changed
- Key design decisions and trade-offs
- Bugs found and how they were fixed
- Verification (test counts, pass/fail status)
- Next steps

<Note>
  Update `DEVLOG.md` when you finish a real session of work, not after every small change. A session typically spans a coherent feature or bug fix.
</Note>

## Reference documentation

The `docs/` directory contains reference material that contributors should keep up to date when changing related code:

| File | Purpose |
| --- | --- |

| `docs/OPCODE_MVP.md` | Checklist of implemented Dalvik opcodes |
| `docs/REFERENCES.md` | External specs: DEX format, Dalvik bytecode, ART interpreter, smali |
| `docs/GOLDFISH_SMOKE.md` | Goldfish kernel boot testing notes |

## Project scope

NekoDroid's APK path is a constrained HLE Dalvik runner, not full Android or ART. Prefer small test APKs without native libraries. If you want to extend the Dalvik interpreter, add the opcode to both `src/android/interp.rs` and `docs/OPCODE_MVP.md`, and include a unit test.

## Commit hygiene

- Do not commit or push from an automated agent. The user owns remotes.
- Squash work-in-progress commits into logical, well-described commits.
- Include test counts in your DEVLOG entry for that session.
- If you add a new opcode, update `docs/OPCODE_MVP.md` in the same commit.

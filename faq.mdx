This FAQ covers common questions about NekoDroid, a browser-native ARMv7 emulator written in Rust and compiled to WebAssembly.

## What does NekoDroid emulate?

NekoDroid emulates an ARMv7-era CPU core, including ARM and Thumb modes, plus VersatilePB peripherals such as PL011 UART, SP804 timer, PL190 VIC, and an 800x600 RGBA VRAM framebuffer at `0x04000000`. It runs in the browser via WebAssembly without plugins.

## Can it run Play Store APKs?

No. NekoDroid includes a constrained high-level emulation (HLE) Dalvik runner that parses `classes.dex` and interprets a subset of Dalvik opcodes with stubbed framework methods. It does not boot Android, run ART, or execute native libraries (JNI). Most real-world APKs need multidex, Binder, Google Play Services, or native code, which are outside the current scope.

For APKs that work today, see [Supported APKs](/android/supported-apks).

## Which browsers are supported?

Any modern browser with WebAssembly support, including Chrome, Firefox, Safari, and Edge. The build uses `vite-plugin-wasm` and `vite-plugin-top-level-await`, which are compatible with evergreen browsers.

## What is the nesting-doll architecture?

The architecture is a stack of emulation layers:

```text
Browser -> Wasm (Rust) -> ARM CPU (+ optional DEX HLE) -> (future) Android OS -> APK
```

The DEX HLE path runs selected APKs without booting a full Android OS. Linux kernel boot helpers exist for research, but full Linux userspace is experimental.

## Is it a full Android emulator?

No. NekoDroid is intentionally a constrained HLE runner. It does not emulate zygote, Binder, SurfaceFlinger, or ART JIT. Full Android bring-up is a long-term research goal.

## How do I build and run locally?

You need Rust stable with the `wasm32-unknown-unknown` target, `wasm-pack`, and Node.js.

```bash
git clone https://github.com/nishal21/NekoDroid.git
cd NekoDroid
npm install
wasm-pack build --target web
npm run dev
```

Open `http://localhost:5173` in your browser.

## How do I run an APK?

1. Build Wasm and start `npm run dev`
2. In the UI, click **Load APK** and choose an APK file
3. Click **Run APK (HLE)**
4. Check the logcat panel and VRAM mode for output

The success signal for the bundled `testdata/hello.apk` is the log line `Hello from NekoDroid`.

## What opcodes does the Dalvik interpreter support?

It supports a minimal viable set, including `move`, `const/4`, `const/16`, `const-string`, `return`, `goto`, `if-*`, `invoke-*`, `new-instance`, array operations, and integer arithmetic. The full checklist is in `docs/OPCODE_MVP.md` in the repository.

## What happens with unsupported opcodes?

The interpreter logs the unsupported opcode hex value and program counter, sets the VM state to halted, and returns an error. The wrapper functions in the Wasm API swallow the error and return a default value so the UI does not crash.

## What happens with unknown native or framework methods?

If `try_invoke` does not recognize a method, it returns `None` and the interpreter attempts to run DEX code. For stubbed framework methods that are recognized but intentionally empty, the stub returns `0` (as an `Int` Value).

## How does the VRAM text blit work?

When an APK calls stubbed text-drawing hooks, the HLE runtime accumulates text lines. Calling `blit_dalvik_text_to_vram()` copies the accumulated text into the emulator's RGBA framebuffer at `0x04000000` so it appears on the canvas. The text is rendered using procedural glyph placeholders, not a real font. The UI can auto-switch to VRAM render mode when running an APK.

## Can I load custom ARM binaries?

Yes. NekoDroid supports loading raw ARM and Thumb binaries, hex programs, and `.bin` ROM files. You can also paste ARM hex into the Custom Program panel and upload it to RAM at address `0x8000`.

## How much RAM can I allocate?

`init_emulator(0)` allocates the default of 512 MiB. The maximum is 4096 MiB. Values above 1024 MiB log a warning about possible browser OOM.

## Does NekoDroid boot Linux?

It includes a `boot_linux_kernel` helper that sets up ATAGs and machine ID `0x46F` (Goldfish) for kernel boot. Full Linux userspace is experimental.

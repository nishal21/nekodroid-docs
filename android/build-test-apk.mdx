NekoDroid ships with built-in test fixtures written in pure Rust, but you can also author your own APKs from Smali. This page shows how to regenerate the committed fixtures using `cargo test`, how to write a minimal Smali program, and how to package it into a ZIP that the HLE interpreter can load.

## Regenerate fixtures with cargo test

Run the in-tree test to rebuild `testdata/hello.apk`, `testdata/hello_println.dex`, and `testdata/bad.apk`:

```bash
cargo test --lib write_fixtures_to_testdata
```

This calls `fixture::build_hello_apk()` and writes bytes to `testdata/`. The `hello.apk` fixture contains:

- `classes.dex` with a single class `Lcom/nekodroid/Hello;`
- A text `AndroidManifest.xml` with package `com.nekodroid` and activity `Lcom/nekodroid/Hello;`
- No native libraries or resources

The `bad.apk` fixture is exactly the bytes `b"not-an-apk"` and is used to verify error handling.

You do not need Android Studio, Gradle, or the Android SDK to rebuild these fixtures. Everything is generated in pure Rust inside `src/android/fixture.rs`.

## Author a minimal Smali program

If you prefer human-readable Dalvik assembly, use [smali](https://github.com/JesusFreke/smali) to assemble `.smali` into `.dex` or `.apk`.

### Step 1: Write Hello.smali

Create a file with this source. It loads a string constant, invokes the HLE `println` stub, and returns.

```smali
.class public Lcom/nekodroid/Hello;
.super Ljava/lang/Object;

.method public static main([Ljava/lang/String;)V
    .registers 2

    const-string v0, "Hello from NekoDroid"

    invoke-static {v0}, Lnekodroid/Hle;->println(Ljava/lang/String;)V

    return-void
.end method
```

### Step 2: Assemble with smali

Install smali and run:

```bash
java -jar smali.jar assemble Hello.smali -o classes.dex
```

This produces a `classes.dex` file with the compiled bytecode.

### Step 3: Package into an APK

An APK is a ZIP file with a specific layout. Package it with any ZIP tool:

```bash
zip hello.apk classes.dex
```

For NekoDroid to read the package name and launcher activity, add a minimal text `AndroidManifest.xml`:

```text
#nekodroid-manifest
package=com.nekodroid
activity=Lcom/nekodroid/Hello;
```

Then include it in the ZIP:

```bash
zip hello.apk classes.dex AndroidManifest.xml
```

Do not add `META-INF`, `resources.arsc`, or `lib/` directories. NekoDroid ignores them, and they add size toward the 32 MiB upload cap.

## Keep bytecode within MVP opcodes

To run in the HLE interpreter, follow these guidelines:

1. Use only integer arithmetic: `add-int`, `sub-int`, `mul-int`, and their `/2addr` variants.
2. Avoid exceptions. Control flow is limited to `if-*`, `goto`, and method calls.
3. Keep arrays one-dimensional. `new-array`, `array-length`, `aget`, and `aput` work.
4. Invoke only HLE stubs or methods you define. Framework calls outside the stub list return `0` silently.
5. Model arithmetic tests after the in-tree `build_arith_dex` fixture pattern:

```smali
    const/4 v0, 0x2
    const/4 v1, 0x3
    add-int/2addr v0, v1
    invoke-static {v0}, Lnekodroid/Hle;->printInt(I)V
    return-void
```

This computes `2 + 3 = 5` and logs `5`.

## Verify in the browser

After packaging, start the dev server and test:

```bash
wasm-pack build --target web
npm run dev
```

Open `http://localhost:5173`, click **Load APK**, select your file, then click **Run APK (HLE)**. Check the logcat panel for output. If the system log says "HLE Dalvik ran 0 steps" and the panel is empty, the VM likely hit an unimplemented opcode. Disassemble your DEX with `baksmali` and compare every instruction against the [supported opcodes](/android/supported-apks#mvp-dalvik-opcodes).

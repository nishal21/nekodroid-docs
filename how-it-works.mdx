NekoDroid is a Rust emulator compiled to WebAssembly that runs entirely in your browser. It exposes two independent execution paths through a single wasm-bindgen bridge: a bare-metal ARM CPU emulator for machine code, and a high-level Dalvik interpreter for APKs. This page explains how both paths work, what they share, and where they diverge.

## Shared bridge

Both paths live inside the same WebAssembly module and linear memory, but they never call into each other. The TypeScript frontend communicates with Rust through wasm-bindgen exports such as `init_emulator`, `run_batch`, `load_apk`, and `run_dalvik_batch`. The frontend also reads MMIO state directly from Wasm memory to update the canvas, audio oscillator, and input registers. This keeps JavaScript boundary overhead low while letting the emulator run large instruction batches inside a single Wasm call.

The CPU state, including all registers and flags, persists across calls in a thread-local instance. You can single-step one instruction, run a batch of thousands, and inspect the result without reloading the program. Batching inside Wasm avoids the cost of crossing the JavaScript boundary on every instruction, which is why NekoDroid can run interactive demos at reasonable frame rates.

## Two independent runtimes

When you press Run or load an APK in the web interface, the Vite + TypeScript frontend calls into Rust. From there, work fans out into two separate paths.

<CardGroup cols={2}>
  <Card title="ARM + Thumb CPU">
    The ARM path runs ARMv7 and Thumb machine code through a fetch, decode, and execute loop. RAM defaults to 512 MB when you call `init_emulator(0)`. The MMU intercepts MMIO addresses for virtual peripherals such as UART, timer, VIC, audio, input, and RTC. Writes to the VRAM base at `0x04000000` render to an 800x600 RGBA canvas.

    Inside `run_batch(count, timer_interval)`, the system timer advances every `timer_interval` instructions. This is a cycle-based tick tied to the instruction batch, not a guaranteed 60 Hz wall-clock timer.
  </Card>

  <Card title="APK Dalvik HLE">
    The APK path bypasses the ARM CPU entirely. `load_apk()` unzips the APK and parses `classes.dex`, then the minimal Dalvik interpreter executes opcodes via `run_dalvik_batch(count)`. The DEX parser reads the header, string pool, type list, method list, and class data before execution begins.

    This is high-level emulation, not the Android Runtime (ART) or a full AOSP stack. Framework calls such as `android.util.Log` and `java.lang.System.out.println` are intercepted and handled natively in Rust. Simple `TextView` and `Activity` hooks are stubbed so basic layout code does not crash. If the interpreter encounters an unknown native or framework method, it returns 0 and continues. Only single-DEX APKs without JNI are supported.
  </Card>
</CardGroup>

## Quick comparison

| What you want to run | Execution path | Key entry points |
| --- | --- | --- |
| Compiled ARM binary (ELF or raw) | ARM + Thumb CPU | `load_rom()`, `run_batch(count, timer_interval)` |
| APK with `classes.dex` | Dalvik HLE | `load_apk()`, `run_dalvik_batch(count)` |
| Linux kernel zImage | ARM + Thumb CPU | `boot_linux_kernel(zImage, initrd)` |

<Note>
  NekoDroid does not run APKs through the ARM CPU, and it does not boot a full Android OS. The Linux kernel boot path is experimental and parses the zImage header, sets ATAGs, and jumps to the start address so the kernel can use the same MMIO peripherals.
</Note>

## Key facts

- **RAM default:** `init_emulator(0)` allocates 512 MB. Larger values are soft-capped at 1024 MB in browser-friendly mode.
- **Timer behavior:** The system timer advances every `timer_interval` instructions inside `run_batch`, not on a fixed 60 Hz schedule.
- **HLE fallback:** Unknown framework or native methods return `0` without stopping the interpreter.
- **Opcode limitation:** Unsupported Dalvik opcodes halt the VM.
